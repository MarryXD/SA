- POST (и PUT в создании). Для создания нового ресурса или добавления чего-либо в существующий ресурс. Например, для создания нового события в календаре, добавления товара в корзину или публикации нового комментария на форуме, запустить процесс\таймер.
- GET. Для получения данных о существующем ресурсе. Например, для просмотра списка доступных рейсов, получения информации о погоде в определенном месте или поиска ближайшей заправки.
- PATCH или PUT. Для обновления существующего ресурса или замены его части. Например, для обновления адреса электронной почты пользователя в базе данных, изменения адреса доставки посылки или изменения деталей бронирования отеля.
- DELETE. Для удаления существующего ресурса. Например, для удаления сохраненного поискового запроса, отмены подписки на услугу или удаления фотографии из аккаунта в социальной сети, завершения процесса или таймера.

POST
=
Предназначен для создания нового ресурса вида объект

* Свойства: Не идемпотентный, не безопасный(т.к влияет на сервер и изменяет информацию), не кэшируемый
* Запрос: POST api.com/users (т.е мы можем обращаться напрямую к коллекциям, хранилищам и тд без указания идентификатора) + тело запроса(со всей необходимой информацией) 
* Ответ: 200ок + заголовок(location: api.com/users/321) + тело ответа(содержит всю информацию о пользователе)
Создаётся новый объект у которого будет новый, назначенный сервером адрес

Для создания искусственной идемпотентности добавляется условно super_id в тело запроса(который генерируется клиентом один раз), который идентифицирует сущность вашего запроса. Таким образом сервер проверяет создавалась ли уже сущность с данным super_id. Т.е на все остальные попытки сервер ответит 208Ок, так как он уже делал эту операцию.

- Тело запроса должно содержать данные, по которым создается новый ресурс. В итоге создается новый ресурс - как будто новый файл. Сервер сам назначает ресурсу ID.
- В теле ответа обычно возвращают либо весь созданный ресурс, включая метаданные об ID ресурса и т. д., либо только метаданные об ID ресурса и т. д..
- Не забывайте про заголовок Location в ответе 
- С помощью отдельного ключа (SuperID) мы можем искусственно сделать POST идемпотентным (как и PATCH)
- Если используем ресурс вида контроллер, просто вызываем POST /controller. В теле запроса передаём данные клиента или всё, что необходимо для выполнения действия над другим ресурсом. Например, мы хотим чтобы контроллер отправил смс ресурсу sms/123 — пользователю 123
  
GET
=
Предназначен для чтения и получения информации

* Пример: GET api.com/users/user123 , api.com/users , api.com/users?age=30
* Свойства: Идемпотентный (всегда возвращается один и тот же ответ), безопасный(т.к не влияет на сервер и не изменяет никакую информацию), кэшируемый
* Запрос: У метода нет тела, следовательно дополнительные параметры передаются через query параметры
* Ответ: Возвращаются Тело, заголовки, код состояния

PUTCH
=
Предназначен для частичного изменения какого либо ресурса

* Свойства: Не идемпотентный, не безопасный(т.к влияет на сервер и изменяет информацию), не кэшируемый
* Запрос: PATCH api.com/users/123/files/123 + тело запроса(помещается информация, которую необходимо изменить)
* Ответ: Возвращаются Тело(вернётся весь файл с новыми изменениями), заголовки, код состояния

- тело запроса должно содержать только изменяемые данные ресурса, а не все его данные. В итоге в ресурс добавляются данные, при этом ресурс не перезаписывается с нуля.
- в теле ответа обычно возвращают весь ресурс в новом виде, с учетом новых добавленных данных.
- мы можем искусственно сделать PATCH идемпотентным
  
PUT
=
Предназначен для создания ресурса с заранее известным id, либо для замены какого то ресурса. Создать ресурс типа users будет неправильно, так как данные id создаются сервером. Но создать коллекцию в файловой системе files он может (т.е взаимодействие возможно с ресурсами типа хранилище)

*Свойства: Идемпотентный (всегда возвращается один и тот же ответ) в контексте данного метода после создания ресурса - сервер начнёт его заменять, но ответ останется таким же - в этом и заключается идемпотентность данного метода, Небезопасный (так как происходят изменения на сервере), Не кэшируемый

Cоздание с id:
* Запрос: api.com/files/123 + тело запроса(например JSON с информацией о файле)
   
* Ответ: Приходит без тела. Т.е только заголовок + код состояния (200ок + информация в заголовке)

Замена (полная замена): 
* Запрос: api.com/files/123 + тело запроса(например JSON с информацией о файле)
  
* Ответ: Приходит без тела. Т.е только заголовок + код состояния (200ок + информация в заголовке)

**PUT используется для**:

- создания ресурса, если клиент может предоставить id для этого ресурса (например, положить файл в хранилище с нужным ему id),

Для создания новых экземпляров ресурса предпочтительнее использование POST запроса. В данном случае при создании экземпляра будет предоставлен корректный идентификатор в возвращённых данных об экземпляре (ведь клиент может ошибиться).

- перезаписи ресурса на новый ресурс с новыми данными (например, перезаписать json, добавив туда cat = 2)

Стандартно мы говорим о ПЕРЕЗАПИСИ файла, то есть замене на новый, а не просто добавлении данных. В этом случае вы должны указать в запросе все данные полностью: оригинальные + новая добавленная часть.

**Важно**. Будьте внимательны с использованием данного подхода. Если с обновлением API вы добавили обязательные поля по умолчанию, то при вызове PUT для обновления они будут добавлены также в файл, вместе с вашими новыми данными.

Но вы свободны в реализации методов «под капотом». Можно использовать частичное добавление данных как в методе PATCH — тело запроса будет содержать только обновляемую часть, полной перезаписи нет. Новые поля по умолчанию не будут добавлены.
