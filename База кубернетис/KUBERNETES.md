Представьте кубер как компанию с начальством и работягами 
=
Есть CONTROL PLANS (мастер нода) - это менеджмент, который принимает решения, там сидят:
1. API SERVER, через который все общаются с кубером
2. SCHEDULER, который решает на какой ноде запустить код
3. CONTROLLER MANAGER, который контролирует чтобы всё работало было как надо
4. ETCD - БД, в которой хранится вся инфа о кластере

Есть WORKER NOD'ы, которые крутят ваши контейнеры, на каждой ноде есть:
1. KUBELET - агент, который общается с CONTROL PLANS
2. KUBE-PROXY, который настраивает сеть
3. CONTAINER RUNTIME, котрый запускает контейнеры

CONTROL PLANS говорит что делать-WORKER NOD'Ы делают
==========================================
POD (под) - минимальная единица, базовая единица развертывания, которую может запустить кубер

И в поде крутится какой-то контейнер с нашим приложением (но в одном поде может быть и несколько контейнеров)

Всё в кубере описывается через YAML Manifests (файлы с описанием, что вы хотите создать)

Создать POD'у можно разными способами.

1. Cамый популярный: kubectl apply -f pod.yaml
2. Через UI
3. Из CI/CD PIPELINE

А всё управление может быть через KUBECTL (посмотреть что получилось, удалить и тд)


Помимо основного контейнера с приложением могут быть и другие чудики, например:

1. INIT-контейнеры, они запускаются перед основным, что-то настраивают и умирают
2. SUDECAR-контейнеры, которые работают параллельно основному (например, собирают логи, проксируют трафик)
3. В поде всегда еще крутится PAUSE контейнер, который настраивает сеть

Но сами по себе поды штука не надежная, упал под - конец
=
Поэтому есть низкоуровневая REPLICASET-клонирование поды (следит, чтобы нужное кол-во подов всегда работало, если что-то упало - то поднимет новый)

Но на деле обычно используют DEPLOYMENT-главный способ запуска приложения в кубере, полноценное управление жизненным циклом приложения, он умеет не только держать нужное кол-во POD-ов, но и умеет грамотно их обновлять, откатывать и маштабировать

Гласная фича-rolling update, кубер может поочерёдно перекатить поды с одной версии на другую: создать новый под с версией 2, ждать пока он запустится и убить старый под версии 1, и так со всеми подами (но стратегию можно и править)

Но как кубер узнает, что под готов принимать трафик? Никак. Для этого нужны пробы, они есть такие:
1. liveness-проверяет жив ли контейнер, если нет-перезапускает
2. readiness-проверяет готов ли контейнер принимать трафик
3. startup-запустился ли контейнер впринципе


Как это работает всё вместе?
=
1. Пишется команда kubectl apply -f deployment.yaml
2. KUBECTL отправляет ваш API в API SERVER
3. API SERVER проверяет валидность и сохраняет это всё в ETCD
4. DEPLOYMENT CONTROLLER (это часть CONTROLLER MANAGER-а) видит всё это и создает REPLICASET CONTROLLER
5. REPLICASET считает сколько ему надо подов и создает их
6. SCHEDULER для каждого пода выбирает ноду (node) — это сервер или виртуальная машина. Можно представлять себе компьютер в дата-центре.
7. KUBELET на выбранной ноде получает задание и дергает CONTAINER RUNTIME
8. CONTAINER RUNTIME тянет образ создает и запускает контейнер
9. Возвращается к KUBELET: он репортит-всё хорошо, всё здорово
