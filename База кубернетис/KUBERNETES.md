Представьте кубер как компанию с начальством и работягами 
=
Есть CONTROL PLANS (мастер нода) - это менеджмент, который принимает решения, там сидят:
1. API SERVER, через который все общаются с кубером
2. SCHEDULER, который решает на какой ноде запустить код
3. CONTROLLER MANAGER, который контролирует чтобы всё работало было как надо
4. ETCD - БД, в которой хранится вся инфа о кластере

Есть WORKER NOD'ы, которые крутят ваши контейнеры, на каждой ноде есть:
1. KUBELET - агент, который общается с CONTROL PLANS
2. KUBE-PROXY, который настраивает сеть
3. CONTAINER RUNTIME, котрый запускает контейнеры

CONTROL PLANS говорит что делать-WORKER NOD'Ы делают
==========================================
POD - минимальная единица, базовая единица развертывания, которую может запустить кубер

И в POD'е крутится какой-то контейнер с нашим приложением (но в одном поде может быть и несколько контейнеров)

Всё в кубере описывается через YAML Manifests (файлы с описанием, что вы хотите создать)

Создать POD'у можно разными способами.

1. Cамый популярный: kubectl apploy -f pod.yaml
2. Через UI
3. Из CI/CD PIPELINE

А всё управление может быть через KUBECTL (посмотреть что получилось, удалить и тд)


Помимо основного контейнера с приложением могут быть и другие чудики, например:

1. INIT-контейнеры, они запускаются перед основным, что-то настраивают и умирают
2. SUDECAR-контейнеры, которые работают параллельно основному (например, собирают логи, проксируют трафик)
3. В поде всегда еще крутится PAUSE контейнер, который настраивает сеть

Но сами по себе поды штука не надежная, упал POD-конец
=
Поэтому есть низкоуровневая REPLICASET-клонирование поды (следит, чтобы нужное кол-во подов всегда работало, если что-то упало - то поднимет новый)

Но на деле обычно используют
